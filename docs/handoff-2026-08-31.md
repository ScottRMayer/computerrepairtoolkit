# Handoff: Portable USB AI PC Repair Kit (Claude Code CLI)

## Objective
Build a portable USB flash drive carrying repair/diagnostic tools, Windows installation ISO(s), and Claude Code CLI. Plug it into a family member's (or the user's own) Windows machine, run the kit, and let Claude Code autonomously diagnose and repair the machine using the bundled tools. The user runs their own Claude Code subscription, on hardware they or their family own.

## Architecture

Claude Code CLI has native bash/file-system access by design. Fully-autonomous mode is confirmed: `claude -p "<task>" --dangerously-skip-permissions` (headless `-p`/`--print` mode plus the bypass flag), or `permissions.defaultMode: "bypassPermissions"` in `settings.json`. A small set of hard-coded refusals survive bypass mode regardless (`rm -rf /`, `rm -rf ~`, `rm -rf $HOME`, explicit `permissions.ask` rules, `AskUserQuestion` always denied) — everything else runs unprompted. The tool whitelist below is the scope of what it should be *told* to use, via a `CLAUDE.md`/instructions file bundled on the USB — a prompted boundary, not a code-enforced sandbox. That instructions file is doing the safety work; write it accordingly.

**Vendor guidance conflict, noted and accepted:** Anthropic's own docs state `bypassPermissions` should only be used in an isolated container/VM "where Claude Code cannot damage your host system," and that it "offers no protection against prompt injection or unintended actions." Native Windows has no Bash sandbox at all (macOS/Linux/WSL2 only). This kit runs bypass mode directly on the bare host by necessity — the task is fixing that host's real filesystem, which a container would prevent. This is the scenario Anthropic's guidance warns against, not a variant of the recommended approach. User has weighed this and accepted it for machines they/family own — not up for re-litigation, but the exact vendor language is worth having on hand if this comes up again.

**Run in normal mode by default. Safe Mode is the fallback**, used only when malware or a broken driver blocks normal operation. Safe Mode disables a large slice of what this toolkit needs (see the constraint table below) — defaulting to it would break the kit for no benefit on a machine that boots normally.

## Safe Mode constraints — verified

Only relevant when falling back to Safe Mode; everything works normally in normal mode.

| Capability | Safe Mode w/ Networking | Note |
|---|---|---|
| `Checkpoint-Computer` (create restore point) | **FAILS** | VSS not in allowlist; MS docs: "This function cannot be called in safe mode" |
| Restoring an *existing* restore point | Works | But cannot be undone when done from Safe Mode |
| `sfc /scannow` | **Works** | Microsoft explicitly recommends running it here |
| `DISM /RestoreHealth` | **Needs `/Source:`** | Windows Update path unavailable — point it at a WIM on the USB with `/LimitAccess` |
| `DISM /ScanHealth`, `/CheckHealth` | Works | |
| Defender on-demand scan (`MpCmdRun -Scan`) | **Works** | `WinDefend` is in both allowlists |
| Defender **real-time protection** | **Also runs** | Filter driver is `Start=0`, loads before allowlist is consulted |
| Defender signature update | **FAILS** | Needs WU stack — bundle the offline definition installer |
| Wi-Fi | **Works** | But use `netsh wlan connect name="SSID"` — the network flyout UI won't render (`NlaSvc` absent, expect false "no internet" indicators) |
| `winget` | **FAILS** (high-confidence inference) | AppX/ClipSVC/TokenBroker all absent — verify in a VM if it matters |
| Windows Update, BITS | **FAIL** | Absent from allowlist |
| Windows Installer (MSI) | **FAILS** | Error 1084 |
| Task Scheduler | **FAILS** | Use `RunOnce`, not `schtasks`, for anything post-reboot |
| WMI / `Get-CimInstance` | **Works** | |
| Event Log / `Get-WinEvent` | **Works** | |
| Tools that load a kernel driver on demand (Procmon, Process Explorer) | **Likely fail** — inference | Autoruns, handle, sigcheck, streams need no driver and are fine |

## Decisions

- **Fully autonomous — no human-approval gate.** User's reasoning: they and their family own the affected computers and are accepting that risk themselves. Settled — don't re-pitch approval-gating.
- **Back up user data before any destructive step.** A restore point covers system state only, explicitly not documents/photos. On a family member's laptop the system is the replaceable part; their files aren't. Copy the user profile to the USB or an external drive as step zero, ahead of anything that removes or modifies.
- **Restore point handling, given the above findings:** create it in **normal mode**, and set `HKLM\Software\Microsoft\Windows NT\CurrentVersion\SystemRestore` → `SystemRestorePointCreationFrequency` = `0` (DWORD) first — otherwise Windows silently skips creation if any restore point was made in the last 24 hours **and still returns success**, which would leave the agent believing it has a rollback it doesn't have. In Safe Mode, substitute `reg export` of touched hives plus file-level copies; a restore point cannot be created there at all.
- **Defender will interfere with the toolkit.** RTP runs in Safe Mode, and several bundled tools (NirSoft, PsExec, AdwCleaner) are routine HackTool/PUA detections. Configure exclusions for the USB tool directory as part of kit startup, or expect binaries to be quarantined mid-run.
- **Tools ship bundled and checksummed on the USB**, fetched fresh from each vendor — never pulled live at repair time. Doubly important in Safe Mode, where `winget` and MSI installs don't work at all.
- **Treat the USB as contaminated after touching a compromised machine.** It's a cross-machine propagation path — scan it before reuse, or use a drive with a physical write-protect switch.
- **Log the run to the USB**, not just the target machine's profile — the transcript is the only record of what an unattended agent did, and it shouldn't live on a machine that may get wiped or handed back.
- **Three tools excluded from the whitelist:**
  - `verifier.exe` — forces a BSOD by design when it finds a driver fault; wrong for unattended use.
  - CCleaner — CLI only does disk cleanup (registry cleaner is GUI-only); `cleanmgr` + BleachBit cover it; supply-chain-compromise history (2017).
  - FRST — fixlist-driven, meaning whatever drives it generates arbitrary registry/file/service edits with no schema constraining it. Manual, human-reviewed use only.

## Tool whitelist (23 tools + 2 pipeline steps)

**Pipeline steps (every session):** user-data backup → restore point (normal mode only, frequency override set) → `Get-CimInstance` system inventory

**Built-in Windows:** `sfc`, `DISM`, `chkdsk`, `MpCmdRun.exe` (Defender), `winget` *(normal mode only)*, `cleanmgr`, `netsh`, `powercfg`

**Sysinternals:** Autoruns/`autorunsc`, Handle, PsList, PsKill, PsService, SDelete, Streams

**Malware/PUP removal:** AdwCleaner, Emsisoft Emergency Kit (`a2cmd.exe`)

**Cleanup:** BleachBit, WizTree

**Disk health:** `smartctl` (smartmontools) — no official portable build; extract from the NSIS installer. `smartctl.exe` itself needs no service, so the extracted binary works standalone.

**Network:** Ookla Speedtest CLI (official)

**Crash/log analysis:** NirSoft suite (BlueScreenView, etc.)

## Blocked / open

- **Does Claude Code CLI run and authenticate from a USB-hosted portable install?** Untested, and everything depends on it. Test in normal mode first, then Safe Mode.
- **Authentication mechanism unresolved.** Claude Code normally uses interactive browser OAuth. Does that work on a target machine (especially in Safe Mode, where shell/UI behavior is degraded)? Fallback is a pre-configured API key on the USB — which means a lost or stolen drive exposes that key.
- **Node.js must be bundled portable** — a broken target machine likely won't have it, and MSI installs don't work in Safe Mode.
- **Windows ISO purpose is undefined.** Currently listed with no decided role: repair-install source, `/Source:` for DISM, clean-reinstall fallback, or all three. This drives which editions to carry and total drive size (ISOs ~5-6GB each; plan 64GB+ USB 3.0). Note that DISM's `/Source:` need makes at least one matching-version WIM genuinely load-bearing, not optional.
- **Windows 10 targets unverified.** All Safe Mode registry findings are from Windows 11 25H2. If any family machine runs Windows 10, run `reg query "HKLM\SYSTEM\CurrentControlSet\Control\SafeBoot\Network"` on it before relying on Wi-Fi or any service above.
- **`winget` in Safe Mode is inference, not confirmed** — no primary source exists. Verifiable in ~30 seconds by booting a VM into Safe Mode and running `winget --version`.
